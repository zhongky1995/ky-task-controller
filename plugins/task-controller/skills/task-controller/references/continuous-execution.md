# Research Ahead, Continue Within Authority

Use when planning complex work, deciding whether to ask the user, or handing off
work whose direction depends on evidence. This is controller behavior, not a new
scenario, mandatory lane, Session, or mandatory execution phase.

For consequential cross-turn continuity, use the durable checkpoint tools in
`inquiry-ledger.md`. They persist inquiry before or during execution without
making inquiry a mandatory phase or changing the user approval protocol.

## Research Before Asking

Read available materials, inspect the current artifact/system, compare plausible
explanations, and use a bounded reversible sample when it can resolve a material
uncertainty. Stay within the user's scope, tool permissions, and planning-only
limits. Do not require a complete contract merely to do relevant read-only discovery.

Stop expanding initial research when the current direction, main risks, and next
authorized action have adequate support. Exhaustive research is not a prerequisite
for production; targeted investigation and verification can continue during it.
If the final form is still unknown, preserve the user's original concern and a
provisional direction rather than inventing a complete production graph.

Ask only for information or a choice that cannot be resolved from accessible
evidence or existing authority. Consolidate related choices that are ready now;
give a recommendation, its evidence, and concrete consequences. Do not ask the
user to judge a technical property that tools or qualified verification can check.
Do not delay an urgent permission or safety question to assemble a larger batch.

## Internal Gates Are Not User Approvals

- Evidence, model, sample-quality, tests, and review checkpoints are normally
  controller/worker checks. Record evidence, then continue the authorized frontier.
- Ask the user for a reserved value/preference decision, scope/budget/commitment
  change, missing authority, or an explicitly required human approval. State the
  precise decision and which work depends on it; continue independent authorized work.
- A sample may pass technical quality without proving the user's preference.
  Ask for sample feedback only when that preference is material and not already
  specified or delegated, or when the user explicitly requested sample approval.
- Existing required userApprovalGate, commercial authority, fingerprint-bound
  approvals, independent verification, and native Session consent still apply.
  Never turn off a required gate or invent consent to reduce interruptions.
- Gate passage, a progress update, and task completion are different events.
  Completing a lane is not a reason to end the turn or request permission again.

A clear build/update request can authorize a bounded execution sequence without
a second ceremonial approval of the controller's own plan. It does not authorize
new visible tasks, publication, spending, or other materially different actions.
An explicit planning-only request or user-requested checkpoint remains a stop.

## Carry Judgment Dependencies Into Execution

Research handoffs describe the uncertainty to resolve, evidence to use, findings
that would change direction, and the consuming decision. Put this in existing
purpose and artifact/input/output contracts; these are not new required API fields.

Independent investigations can run together. Production that depends on an
unresolved decision must wait for that decision, not simply a research document's
existence. The decision is made by the controller within delegated authority or
by the user when reserved. Do not invent user feedback to unlock downstream work.

Within the approved scope, run discovery, production, and verification continuously
with internal checkpoints. Use the existing orchestration, dispatch, and recovery
mechanisms; this reference grants no additional runtime or write permissions.

## Evidence Can Change The Plan

Inquiry, execution and review can alternate within the same purpose. They are not
fixed stages that must each run once. Distinguish:

- an implementation adjustment inside the accepted scope: adapt and continue;
- an unresolved premise: investigate the relevant uncertainty and preserve valid
  findings, rather than restarting everything or asking the user to diagnose it;
- a changed goal, reserved tradeoff or permission: explain the substantive change
  and obtain only the input/authority actually missing before dependent action.

Discussion-only authority does not become implementation authority when an idea
looks promising. Existing execution authority does not vanish at an internal
checkpoint. New user feedback may expand the design space; compare meaningful
possibilities before selecting, without manufacturing a fixed number of options.
Useful iteration is progress when it changes understanding or closes a real
gap. Reduce repeated misunderstanding and duplicate administration, not the
number of user contributions or review rounds.

Keep observations, candidate explanations, user preferences, and approved decisions
distinct. A new source may invalidate an assumption without correction keywords;
a question or quoted phrase may contain those keywords without changing intent.
The current feedback classifier is heuristic, not proof of semantic understanding.
Check the actual meaning and affected premise before treating text as a change.

For a confirmed contract impact, use the existing correction/revision protocol,
record the evidence and affected requirements, and reconcile obsolete work. If a
correction is already open, resolve it through revision; never bypass its gates.
Unknown impact requires targeted checking, not an automatic pass or automatic
request for the user to diagnose it. Explain what remains valid and what changed.

The runtime still invalidates an ordered suffix and requires new state for certain
topology changes. This guidance does not implement dependency-local migration or
automatically stop host workers. Preserve stop evidence and capacity accounting.

## Synthesize For The Intended Use

The controller integrates contributions into an answer, judgment, proposal or
usable artifact appropriate to the request. Resolve or disclose conflicts and
missing connections; multiple passing lane reports are not themselves a coherent
result. A useful explanation can be a complete outcome without implementation.

Match consequential claims to evidence: distinguish what a worker reported,
what has been checked, and what remains conditional. Check relevant source,
artifact, readback or user-path evidence according to the domain and risk; do not
add a universal software-style release pipeline or recheck every minor output.
User acceptance supports preference/authority, not factual or technical truth.
State limitations where they affect use; do not bury them beneath test counts.

Keep internal coordination detail out of the main delivery unless it helps the
user act. The user should receive the usable result and its important boundaries,
not be asked to reconcile worker drafts, versions or competing conclusions.

## Behavioral Review Cases

Check decisions, not exact wording, when evaluating this protocol:

| Situation | Expected behavior |
| --- | --- |
| User requests an update with clear boundaries | Inspect, make a bounded plan, execute and verify; no extra plan-approval round |
| User says to research only and wait | Inspect and recommend; no production or worker creation |
| Three independent evidence checks complete | Controller evaluates them and continues; no three user confirmations |
| Sample passes tests but an undelegated direction choice remains | Present concrete alternatives/recommendation and wait only on dependent production |
| Required commercial approval has no current fingerprint approval | Keep the gate blocked; overall execution approval is insufficient |
| New evidence contradicts an accepted premise without keywords | Assess impact and revise affected work if confirmed; do not silently continue |
| User asks why something is wrong but says not to change it | Diagnose; do not infer implementation authority from correction words |
| Missing source affects one branch only | Investigate or ask for that source; continue independent authorized work |
| User introduces a new creative mechanism | Explore its consequential possibilities; do not silently freeze the first suggested implementation |
| Evidence supports a candidate but user choice is reserved | Keep support distinct from selection; seek only the missing choice |
| Two research workers disagree | Compare evidence/assumptions and synthesize a qualified conclusion, not two pasted reports |
| A bounded revision closes a real gap | Retain valid work and recheck affected claims; do not count the round itself as failure |
| Worker reports a consequential external action completed | Check relevant target evidence before declaring it verified; report uncertainty if inaccessible |

These are review cases, not a claim of automated semantic or live-session coverage.
